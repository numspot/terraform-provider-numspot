# Contributing to the Numspot Terraform Provider

Thank you for your interest in contributing! This document covers how to build,
test, and submit changes to this repository.

## Code of Conduct

Contributions are governed by our [Code of Conduct](.github/CODE_OF_CONDUCT.md).
By participating, you are expected to uphold it.

## Getting started

Requirements:

- [Terraform](https://developer.hashicorp.com/terraform/downloads) >= 1.0
- [Go](https://golang.org/doc/install) >= 1.27

Go-based tooling is managed by the repository:

- `terrafmt` and `tfplugindocs` are pinned as `go tool` dependencies in `go.mod`.
- `golangci-lint` is installed locally into `bin/` by `make setup`.

```sh
git clone https://github.com/numspot/terraform-provider-numspot.git
cd terraform-provider-numspot
make setup
go build ./...
```

## Development workflow

Most resources and data sources are **generated** from a per-resource
descriptor, then refined by hand. If you add or change a resource, follow the
descriptor-driven flow described in
[docs/internal/ADDING_A_FEATURE.md](docs/internal/ADDING_A_FEATURE.md) — do not
hand-edit `*_gen.go` or `*_spec.json` files.

### Repository rules

- `make fmt` — format Go (golangci-lint fmt), embedded HCL (terrafmt) and
  `examples/` (terraform fmt). Run it before every commit.
- `make lint` — run golangci-lint with the project configuration.
- `make audit` — check naming conventions, override `reason`s, residual `TODO`s.
- `make check-scaffold-drift` — verify that resources with
  `scaffold_check: true` still match their descriptors. If drift is reported,
  run `make fix-scaffold-drift` and re-check.
- `make check-registry-drift` — verify that
  `docs/internal/RESOURCE_REGISTRY.md`, `OWNERS.md` and `.github/CODEOWNERS`
  were regenerated from `docs/internal/resources-registry.yaml`.
- `go build ./... && go vet ./...` — must pass cleanly.

### Documentation

Provider documentation under `docs/` is generated by tfplugindocs. After
changing a schema or `templates/index.md`, run:

```sh
make docs
```

## Testing

### Unit tests

```sh
go test -race ./...
```

### Acceptance tests (offline, VCR)

Acceptance tests run against recorded HTTP cassettes and replay them offline —
no Numspot account or network access is needed:

```sh
make testacc
```

To record new cassettes (requires valid Numspot credentials and a Space ID):

```sh
make record-cassettes
```

This runs the same suite with `VCR_MODE=record`. Review the recorded cassettes
before committing: they must only ever contain the `FAKE_TOKEN` placeholder, no
real credentials.

## Committing and opening a pull request

1. Fork the repository (or create a branch) and open a **draft PR** early if
   the change is substantial.
2. **Conventional Commits** are enforced on every commit and on the PR title:
   `feat:`, `fix:`, `chore:`, `docs:`, `test:`, `ci:`, `refactor:`, …
   Dependency bumps are committed as `fix(deps):` (gomod) or `chore(deps):`
   (GitHub Actions).
3. Keep PRs focused; squash-merge is used on `main`.
4. The CI runs the same gates as local development: generated-code drift,
   `go vet`, `go build`, `go test -race`, golangci-lint, scaffold/registry
   drift checks, offline acceptance tests, govulncheck, gitleaks, and
   Conventional Commits.

Releases are managed by [release-please](https://github.com/googleapis/release-please):
a release PR accumulates Conventional Commits, and merging it cuts the next
`v*` tag, which triggers the Release workflow.

## Reporting issues

Please search the existing issues before opening a new one. For security
vulnerabilities, do **not** open a public issue — follow
[SECURITY.md](SECURITY.md) instead.
